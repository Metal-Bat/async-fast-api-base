# OBS-001 — Prevent telemetry diagnostic feedback

Backlog: OBS-001
Date: 2026-10-02
Area: core/observability

## Summary

The OTLP logging handler excludes OpenTelemetry SDK and exporter diagnostics. Application
records continue to export; configured console/file handlers continue to receive diagnostics.

## Why

Exporter failures logged through the root handler could become new export work and produce
repeated failures. SDK warnings raised while translating a log record could re-enter the handler
and trigger its recursive-logging protection.

The reported connection resets contain HTTP exporter messages, although the current source
explicitly constructs gRPC exporters. An older image or a separately configured HTTP exporter
targeting the gRPC receiver is suspected, but cannot be confirmed without the failing deployment.

## What Changed

- Added a handler-specific filter for `opentelemetry` and its child logger names in
  `src/core/observability.py`. Other handlers and application logger names are unaffected.
- Added scheduler-configuration regression tests using an in-memory log exporter. Tests verify
  application/JSON logs, local diagnostics, gRPC exporter classes, and the common configured
  endpoint for all three signals.
- Documented the Compose gRPC endpoint and image rebuild/recreation procedure in `README.md`.
  Existing exporter transport and Collector receiver settings were already aligned and remain so.

## Architecture

No architecture change.

## Compatibility

No API, DTO, migration, or dependency changes. OpenTelemetry diagnostic records are no longer
sent to OTLP; use configured console/file outputs for these diagnostics. Compose continues to
use `http://otel-collector:4317` with explicit gRPC exporters. Recreate application processes to
load the filter; rebuild outdated application/Collector images as documented in the README.
