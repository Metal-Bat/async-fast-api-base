# DB-001 — Consolidate Alembic into one initial revision

Backlog: DB-001
Date: 2026-10-02
Area: migrations

## Summary

Replaced 33 revision files with `src/migrations/versions/b13a0c7d2e44_initial_schema.py`.
It is the sole root and head, retaining the former head identifier. Fresh databases receive
the same complete schema and seed data; fully upgraded databases remain current.

## Why

The user requested one migration file. Rebuilding solely from current entity metadata would
omit frozen seed contracts and database functions/triggers, so consolidation preserves the
original operations and execution order.

## What Changed

- One self-contained revision owns all schema operations, seed data and PostgreSQL guards.
  Private domain stages isolate local variables and retain the former operation ordering.
- Duplicate helper names were made domain-specific. Upgrade calls stages in dependency order;
  downgrade calls them in reverse order. No runtime entity imports or `metadata.create_all`
  are used by the revision.
- Migration tests now load the consolidated revision and enforce one file with no parent,
  the retained head ID, UUID idempotency keys, and seed contracts.
- README documents fresh installation, existing-head compatibility, earlier-revision deployment
  requirements and the loss of intermediate downgrade targets.

## Architecture

### Before

A linear chain of 33 revisions from `d28db6215a2b` to `b13a0c7d2e44`.

### After

One root/head revision, `b13a0c7d2e44`, with all frozen operations in one file.

### Reason

Fulfill the requested consolidation while preserving database behavior and avoiding replay on
databases already at the former head.

## Compatibility

- No application schema, API, DTO or dependency changes.
- Fresh databases use `alembic upgrade head`.
- Databases already at `b13a0c7d2e44` require no stamp or data migration.
- Databases at intermediate revisions must upgrade using the previous full chain before this
  checkout is deployed. Stamping an incomplete database does not apply the missing operations.
- Downgrade to base removes the entire application schema. Intermediate revision targets have
  been removed. Historical seed audit identifiers are preserved.
