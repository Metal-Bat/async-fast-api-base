# DB-002 — Separate schema and required data

Backlog: DB-002
Date: 2026-10-09
Area: migrations

## Summary

Replaced the ten-file chain with exactly two frozen revisions:
`0001_schema` creates the complete current schema; `0002_required_data` installs required data.
The explicit owner request supersedes the previous additive-only repository migration policy.

## Why

The owner requested two files: one for all code tables and one for required reference data.
The previous chain mixed schema and data and had accumulated nine successors. Retaining frozen
DDL rather than creating tables from live entity metadata preserves PostgreSQL guards and exact
immutable catalog contracts.

## What Changed

- Schema creation includes every current application/history table, indexes, constraints,
  comments, UUID functions and published-record/runtime guards. No seed rows are inserted.
- Required data retains every frozen handler version, port contract and seed audit identifier,
  report cleanup and abandoned-upload cleanup schedules. Also installs four frozen deployed
  extension handlers (AI decision, connection status,
  permission check and request priority). Installs the thirteen current
  permission definitions with no roles or assignments. Optional admin credentials remain a
  complete environment pair; no fixed credentials or demo data are introduced.
- Initial handler versions now enter as drafts and publish after their ports are inserted,
  satisfying the immutability guards already installed by the schema revision. Publishing is
  scoped to the supplied initial/extension contracts, preserving unrelated user-authored drafts.
- Automation operations are code-owned registries; there is no operation table to populate.
  Private connection credentials, external integration activation and demo installation stay
  outside migrations.
- Unique new revision IDs refuse legacy markers before DDL replay. Full teardown works on
  disposable databases. Data-only downgrade is refused because published catalogs can be in use.
- Updated deployment instructions, current migration decision and regression coverage.
  Historical change records retain their original facts and revision IDs.

## Architecture

### Before

Ten linear revisions; the initial revision mixed schema, seed data and guard installation.

### After

Two revisions separate complete schema creation from required data installation. Private domain
stages retain DDL dependency order; data enters published contracts through the installed guards.
Runtime modules, layers, entities and HTTP interfaces are unchanged.

### Reason

Make schema-only and complete installation explicit while preserving the existing database design.

## Compatibility

Fresh databases can run `alembic upgrade head` or `alembic upgrade 0001_schema` for tables only.
Application tables and API contracts are unchanged. Permission definitions grant no access alone.

Existing legacy databases are not automatically compatible with the new IDs. Keep the previous
checkout and migrations for upgrading them to the former complete head. Back up and restore to
an isolated copy; compare complete schema, constraints, comments, functions and triggers with
this baseline, verify retained catalogs, and run application acceptance checks. Reconcile missing
permissions and deployed drafts with `scripts/reconcile_system_catalog.py` without optional role flags; existing
operator grants/revocations must survive. Review and publish newly installed trusted extension
versions through the existing authorized catalog lifecycle. Only after these checks may an
operator deliberately
rebaseline its revision marker to `0002_required_data`. Do not replay seed inserts or stamp an
incomplete schema. No shared/project database transition was executed in this task.

Rollback an existing deployment from its verified backup/previous checkout. Do not downgrade
required catalogs independently. Full downgrade to base removes all application tables and data.
